Why teams pick Supatype

01

Migrations you can review

Supatype diffs your types against the live database, classifies each change, and never renames or drops a column without your approval.

02

Row and column access from one set of rules

Write read, create and update rules next to the model, down to individual fields. Row rules compile to Postgres RLS policies. Field rules hide columns per role with supatype_mask, or through generated views where the extension isn't installed.

03

Studio, a CMS built from your types

Your types are the content model. Studio reads them and generates the CMS your content team uses: list views, edit forms, rich text, a media library and role-based editing. Add a field to a type and editors get it on the next push.

04

Storage with permissions

File and image fields get buckets with matching rules, plus image transforms and signed URLs.

Realtime

Subscribe to model changes. Events, deletes included, reach only subscribers allowed to read the row.

APIs and a typed client

QUICK START

Three commands to
a running stack.

1. INSTALL
$ npm install -g @supatype/cli
2. INIT
$ supatype init
3. DEV
$ supatype dev

supatype dev applies your types, watches for changes, migrates the database and regenerates the client. supatype push applies them to staging or production. Runs in Docker by default. Local development covers native mode, ports and the frontend proxy.

NAME
supatype - one set of types, database to component
WHAT DO I ACTUALLY WRITE?
TypeScript types and the access rules next to them. Supatype generates the tables, migrations, policies, API, client and Studio from those.
CAN I SELF-HOST?
Yes. Docker Compose on any VM, with the same project layout as local development. See the self-hosting guide.
WHICH DATABASES?
Postgres 17, shipped as our own image.
HOW IS IT LICENSED?
SDKs are MIT. CLI and services are Apache 2.0. The schema engine is BSL 1.1. See licensing.
