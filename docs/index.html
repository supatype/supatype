02

Row and column access from one set of rules

Write read, create and update rules next to the model, down to individual fields. Row rules compile to Postgres RLS policies. Field rules hide columns per role with supatype_mask, or through generated views where the extension isn't installed.

03

Studio, a CMS built from your types

Your types are the content model. Studio reads them and generates the CMS your content team uses: list views, edit forms, rich text, media and role-based editing. Add a field to a type and editors get it on the next push. Studio

QUICK START

Three commands to
a running stack.

1. INSTALL
$ npm install -g @supatype/cli
2. INIT
$ supatype init
3. DEV
$ supatype dev

supatype dev applies your types, watches for changes, migrates the database and regenerates the client. supatype push applies them to staging or production. You need Node 22 or newer, and Docker running for the default mode. Local development covers native mode, ports and the frontend proxy.

NAME
supatype - one set of types, database to component
WHAT DO I ACTUALLY WRITE?
TypeScript types and the access rules next to them. Supatype generates the tables, migrations, policies, API, client and Studio from those.
CAN I SELF-HOST?
Yes. Docker Compose on any VM, with the same project layout as local development. See the self-hosting guide.
WHICH DATABASES?
Postgres 17, shipped as our own image.
HOW IS IT LICENSED?
SDKs are MIT. CLI and services are Apache 2.0. The schema engine is BSL 1.1. See licensing.
WHAT IF WE LEAVE?
Your data stays in ordinary Postgres tables, and access rules are ordinary row level security policies, so the database keeps working with Postgres and PostgREST without the CLI. Migration history stays in the _supatype schema, and supatype migrate -o file.sql writes a change as plain SQL. Model hooks run in the Supatype server, so those would need a new home.
WHAT IF A RULE CANNOT EXPRESS MY POLICY?
A model hook runs a handler of yours before a write through the API, and can refuse it. A hook is not a security boundary, because direct SQL skips it. There is no raw SQL rule type, on purpose. A push leaves policies you wrote by hand in place and reports them, and supatype adopt decides which objects Supatype owns. See model hooks.
WE ALREADY USE AUTH0.
Supatype issues its own tokens, and auth.claim() reads any claim in them. Accepting tokens from another issuer directly is not supported yet. Book a call if you need it.
HOW ARE ACCESS RULES TESTED?
Against a real Postgres 17 in CI on every change: generated policies, field access, attempts to leak masked values through filters and ordering, and every field type against one shared fixture.
FOUND A SECURITY ISSUE?
Email hello@supatype.com privately rather than opening a public issue. Details are in security.txt.
