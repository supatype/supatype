How it works

One set of types,
and everything that usually drifts from it.

Your stack describes the same data in six places, on both sides of the network. Supatype has one. One set of types runs your whole stack, database to component. Rename a field and the build fails instead of production.

01

Migrations you can review

The schema engine diffs your types against the live database, detects renames instead of dropping columns, and classifies every change before it runs.

02

Access rules that compile to RLS

Declare who can read, create and update next to the model. Supatype writes the Postgres row-level security policies for you.

03

Studio, built from the schema

List views, edit forms, rich text and a media library for your editors. Add a field to the type and it appears with the right widget.

04

Storage with permissions

File and image fields get a bucket with matching access rules. Image transforms and signed URLs are included.

05

Realtime

Subscribe to changes on any model from the client, with row-level security enforced on every event.

06

APIs and a typed client

REST through PostgREST, GraphQL through pg_graphql, OpenAPI docs, and a TypeScript client generated from the same types.

How it compares

Where the types
stop.

  • tRPC End-to-end types across the API. You still write the database and policies.
  • Prisma Schema to types. Stops at the client.
  • Supabase A backend. Types introspected after the fact.
  • Supatype One set of types, database to component.
Quick start

Four commands
to a running stack.

Supatype runs the stack in Docker by default. Local development covers native mode, ports and the frontend proxy.

$ npm install -g @supatype/cli
$ supatype init
$ supatype dev
$ supatype push
Self-hosting

Run it on
a server you own.

Docker Compose on any VM, with the same project layout you use locally. Images come from Docker Hub; put a reverse proxy in front for HTTPS.
