How it works

One schema, and everything that usually drifts from it.

A backend and a CMS normally describe the same data twice. Supatype reads your types once and generates each layer from them, so a rename breaks the build instead of production.

01

Migrations you can review

The schema engine diffs your types against the live database, detects renames instead of dropping columns, and classifies every change before it runs.

02

Access rules that compile to RLS

Declare who can read, create and update next to the model. Supatype writes the Postgres row-level security policies for you.

03

Studio, built from the schema

List views, edit forms, rich text and a media library for your editors. Add a field to the type and it appears with the right widget.

04

Storage with permissions

File and image fields get a bucket with matching access rules. Image transforms and signed URLs are included.

05

Realtime

Subscribe to changes on any model from the client, with row-level security enforced on every event.

06

APIs and a typed client

REST through PostgREST, GraphQL through pg_graphql, OpenAPI docs, and a TypeScript client generated from the same types.

Get started

Local development

Install the CLI, scaffold a project, and run the full stack on your machine. Supatype runs it in Docker by default; choose Native during supatype init if you would rather use host binaries and no Docker.

1

Install the CLI

$ npm install -g @supatype/cli

The first run downloads the binaries it needs into ~/.supatype/cache/.

2

Create a project

$ mkdir my-app && cd my-app
$ supatype init
$ npm install
$ supatype keys

supatype init writes package.json, supatype.config.ts, a starter schema and public/. Add the keys it prints to .env if they are not there already.

3

Start the stack and push your schema

$ supatype dev
$ supatype push

The gateway serves REST at /rest/v1/, auth at /auth/v1/, storage and realtime. With Docker it listens on http://localhost:18473 (init picks a free port per project and writes it to .env); with Native it listens on http://localhost:54321.

+

Serve your frontend dev server at /

Keep the committed supatype.config.ts pointing at your production build, and proxy to Vite or Next from a gitignored supatype.local.config.ts: 

// supatype.local.config.ts (your machine only)
export default {
  app: { mode: "proxy", upstream: "http://localhost:5173" },
}

Restart supatype dev after changing config. The APIs stay on their own paths.

Get started

Self-hosting

Run the whole platform on a server you own with Docker Compose. The project layout is the same one you use locally, so the repository you develop in is the one you deploy.

1

Prepare the server

Ubuntu 22.04 or similar, Docker with Compose v2, Node.js 22 or later, and the CLI:

$ npm install -g @supatype/cli
2

Scaffold and set secrets

$ mkdir my-app && cd my-app
$ supatype init
$ npm install
$ supatype keys

Set a strong JWT_SECRET and your public URLs in .env.

3

Start Compose

$ supatype self-host compose render
$ supatype self-host compose up -d
$ supatype push

The gateway listens on http://<your-host>:18473 with Studio at /studio/. Put a reverse proxy in front for HTTPS.

Images come from Docker Hub at :latest: supatype/postgres:17-latest, supatype/server (which includes realtime), supatype/storage, supatype/studio, supatype/schema-engine, supatype/functions-worker and supatype/control-plane. Pin versions with SUPATYPE_*_IMAGE in .env if you need to.

4

Serve a static app

$ supatype app add --static ./public

This writes app.mode: "static" to supatype.config.ts. Commit it; it is a one-time step, not something to repeat on the server.

Deploy changes

Local and self-hosted environments read the same committed config. What differs between machines lives in files you do not commit.

Which file holds what

FileHoldsCommit
supatype.config.tsSchema path, app routing, version pinsYes
supatype.local.config.tsOverrides for your machine, such as the dev proxyNo
.envDATABASE_URL, JWT keys, API_EXTERNAL_URLNo

What to run when something changes

ChangeLocalSelf-hosted
Schema supatype push supatype push
Frontend Nothing with the dev proxy; otherwise npm run build npm run build, then compose render and compose up -d
supatype.config.ts Restart supatype dev compose render and compose up -d
.env Restart supatype dev compose up -d

A typical server deploy

$ cd my-app
$ git pull
$ npm install           # if package.json changed
$ supatype push         # schema migrations
$ npm run build         # static files into public/ or dist/
$ supatype self-host compose render
$ supatype self-host compose up -d
NOTE Point DATABASE_URL in the server's .env at the Compose Postgres on localhost:5432, so push and Studio use the same database as the stack.
Operate

Upgrading Supatype

Moving to newer Supatype components is separate from deploying your own changes, and it takes two commands, not one. 

$ supatype update      # pull new images and binaries
$ supatype push        # apply the schema those components expect
$ supatype self-host compose up -d

The push is the step that is easy to miss. Grants, policies, functions and buckets are generated from your schema and only reach the database through push, so new images on an older database can refuse rules until it runs. The upgrade is finished after the push, not before.

403S AFTER AN UPGRADE This is the usual cause. The storage service logs the reason and names supatype push as the fix.
