Studio roles

Everyone who signs in to Studio has a Studio role. The role decides which screens they see and what they may change.

Pre-1.0: APIs and config may change between releases.

The four roles

A self-hosted project has four Studio roles:

Admin

Everything, including giving and removing Studio roles.

Developer

Everything an admin can do, except Studio roles.

Editor

Content and files. No schema, SQL or settings.

Viewer

Reads content, files, schema and logs. Changes nothing.

Supatype Cloud adds owner and billing roles for the organisation.

NOTE

A Studio role is separate from your app. It grants nothing in your own application, and Role<> rules in the schema do not read it.

SQL EDITOR

The SQL editor runs as the database owner. Row level security does not apply there, and masked columns show in full. Every query is recorded.

BUCKET RULES

A bucket's access rules page is part of "see the access rules". Viewers see it read-only. Editors cannot open it today. A change in progress shows it to editors read-only too. Only admins and developers can change the rules.

Full access and Studio mode

Admins and developers work with full access. Studio acts for them as the service role, so your app's access rules and field masks do not apply. An amber "Full access" banner shows while project rows are on screen. Every change is recorded.

Editors and viewers work in Studio mode. Your app's row rules are skipped, so the Studio role decides which rows they reach. Field rules still apply, so masked columns stay masked. Every change is recorded.

There is no switch for this on content screens. To see data as an app user would, use Send as.

Field masking

A column with a field rule shows a padlock in Studio:

  • A padlock alone: the value is hidden from you.
  • A padlock with a question mark: the column is restricted per record, and this value is hidden or empty.
  • A value with a small padlock: you can see it, but other callers may not.

In forms, a column you cannot read shows the padlock. A column you can read but not write is disabled. Admins and developers see every value with the small padlock, because masks do not apply to full access.

Send as

The API page's Try it, the GraphQL explorer and a function's Invoke tab ask who to send the request as:

ChoiceSendsOffered to
Me (default)Your own token. Your app's access rules apply to youEvery role
AnonymousThe anon key, as a visitor who is not signed inEvery role
Service roleThe service role. No rules apply. The key never reaches the browserAdmins and developers
A token I pasteA token you paste, such as a test user'sEvery role

The choice applies to one request and is not remembered. The Invoke tab is on the Edge Functions page, which only admins and developers can open.

Drafts and publishing

On a model with drafts, the record editor shows Save draft and Publish. Its menu also schedules, discards and unpublishes.

Admins, developers and editors see drafts by default. Change this with publishing.draft_visibility in supatype.config.ts. A role that cannot see drafts does not get the publish controls.

In the Data browser, saving a cell or adding a row on a drafts model asks first:

  • Save as draft: the change is stored as a draft, and a new row is created unpublished. The cell keeps the live value with a Draft badge until the record is published.
  • Save and publish: the change goes live now, with any earlier draft changes to that record. A new row is created and published.
DELETES ARE PERMANENT

Deleting a row in the Data browser deletes it for good. It does not make a draft.

Giving someone a role

In Studio, open Authentication > Users. The Studio access column shows each user's role. An admin can change it there, or choose No access. Other roles see it read-only. Your own row cannot be changed.

Create User has a Studio access choice too. Only admins see it.

From the command line:

terminal
$ supatype admin create-user --email sam@example.com --role editor
$ supatype admin set-role --email sam@example.com --role viewer
$ supatype admin list-users

create-user makes a new sign-in user with a Studio role. --role is admin, developer, editor or viewer, and defaults to admin. It asks for the password if you leave out --password. supatype dev and supatype push make sure a first admin exists.

CLI

The CLI writes the database directly. It does not run the checks Studio runs, such as keeping the last admin.

Only admins change admins

  • Only admins give, change or remove Studio roles.
  • A developer cannot change an admin's account: no disabling, deleting, password or email changes, MFA changes, signing out or sending links. The server refuses with "Only a Studio admin can change another admin's account."
  • Nobody can change their own Studio role or remove their own access.
  • The last admin cannot be removed. Make someone else an admin first.
