Get started

Run the stack on your machine, self-host it with Docker Compose, ship changes and upgrade Supatype components.

Pre-1.0: APIs and config may change between releases.

Local development

Install the CLI, scaffold a project, and run the full stack on your machine. Supatype runs it in Docker by default. Choose Native during supatype init if you would rather use host binaries and no Docker.

1

Install the CLI

terminal
$ npm install -g @supatype/cli

The first run downloads the binaries it needs into ~/.supatype/cache/.

2

Create a project

terminal
$ mkdir my-app && cd my-app
$ supatype init

supatype init writes package.json, supatype.config.ts, a starter schema and public/, installs dependencies with your package manager and writes the API keys to .env. Run npm install or supatype keys yourself only if you passed --no-install or --no-keys.

3

Start the stack

terminal
$ supatype dev

supatype dev applies your schema when it starts, then watches it: each save migrates the database and regenerates the typed client. It keeps running, so use a second terminal for other commands. supatype push applies the schema to another database, such as a server you deploy to.

It stops with its stack when the process that started it exits, as it does on Ctrl+C: a script that is killed, or a cancelled CI job, leaves nothing running. To leave a stack running with nothing attached, use supatype self-host compose up -d.

If dev itself is killed (its process ended, or its window closed before it finished stopping), the stack can be left running. The next supatype dev finds it and offers to stop it, and supatype self-host compose down stops it now.

The gateway serves REST at /rest/v1/, auth at /auth/v1/, storage and realtime. With Docker it listens on http://localhost:<gateway-port>: init picks a free port per project and writes the URL to .env as API_EXTERNAL_URL (the port alone is SUPATYPE_KONG_PORT). With Native it listens on http://localhost:54321.

+

Serve your frontend dev server at /

Keep the committed supatype.config.ts pointing at your production build, and proxy to Vite or Next from a gitignored supatype.local.config.ts:

supatype.local.config.ts
// supatype.local.config.ts (your machine only)
export default {
  app: { mode: "proxy", upstream: "http://localhost:5173" },
}

Restart supatype dev after changing config. The APIs stay on their own paths.

Self-hosting

Run the whole platform on a server you own with Docker Compose. The project layout is the same one you use locally, so the repository you develop in is the one you deploy.

1

Prepare the server

Ubuntu 22.04 or similar, Docker with Compose v2, Node.js 22 or later, and the CLI:

terminal
$ npm install -g @supatype/cli
2

Scaffold and set secrets

terminal
$ mkdir my-app && cd my-app
$ supatype init

init installs dependencies and writes generated secrets and API keys to .env. Set your public URLs there.

3

Start Compose

terminal
$ supatype self-host compose render
$ supatype self-host compose up -d
$ supatype push

The gateway listens on http://<your-host>:<gateway-port>, the port in SUPATYPE_KONG_PORT in .env (18473 when it is unset), with Studio at /studio/. Put a reverse proxy in front for HTTPS.

REST BEFORE THE FIRST PUSH

Until the first supatype push, every REST request answers 503 with PGRST002: PostgREST will not serve until the schemas it exposes exist, and the push creates them. After a push PostgREST can take up to about 30 seconds to notice, so push waits (at most 40 seconds) until REST answers, printing one line while it does.

ALLOWED ORIGINS

Browsers may call the API from the origin of SITE_URL and from the origins in api.corsOrigins (supatype.config.ts) or SUPATYPE_CORS_ALLOW_ORIGINS (.env). Any other origin is refused. Owners and admins can change the list in Studio, on the Settings page's CORS tab: a saved list is kept in the database and replaces the default until it is reset. The site URL stays allowed whatever is saved. * allows every origin, and only when you write it.

PORTS

Only the gateway is published on every interface, at SUPATYPE_KONG_PORT. Postgres (SUPATYPE_DB_PORT, default 5432), the API server (SUPATYPE_SERVER_PORT, default 9999) and SeaweedFS (SUPATYPE_SEAWEEDFS_PORT, default 8333) bind 127.0.0.1, so they are reachable from the server itself and nowhere else. To reach them from other machines, set SUPATYPE_PUBLISH_ADDRESS=0.0.0.0 (or one interface's address) in .env and run supatype self-host compose up -d. Put a firewall in front first. supatype init lists these variables, commented out, in .env.

Images come from Docker Hub at :latest: supatype/postgres:17-latest, supatype/server (which includes realtime), supatype/storage, supatype/studio, supatype/schema-engine, supatype/functions-worker and supatype/control-plane. Pin versions with SUPATYPE_*_IMAGE in .env if you need to.

Every function is handed two addresses. ctx.url is for calling the API from inside the function. Under Docker it is http://kong:8000, which no browser can open. ctx.publicUrl is the project's public address, API_EXTERNAL_URL in .env, for links you give to people.

Functions get no database connection by default. Setting SUPATYPE_FUNCTIONS_DB_URL in .env hands every function that URL as ctx.dbUrl: a raw Postgres connection as whichever role it names, which bypasses row rules and field masking. Point it at a least-privilege role granted only what your functions need, never the admin URL, for example postgresql://functions_reader:<password>@db:5432/my-app.

4

Serve a static app

terminal
$ supatype app add --static ./public

This writes app.mode: "static" to supatype.config.ts. Commit it. It is a one-time step, not something to repeat on the server.

Deploy changes

Local and self-hosted environments read the same committed config. What differs between machines lives in files you do not commit.

Which file holds what

FileHoldsCommit
supatype.config.tsSchema path, app routing, version pinsYes
supatype.local.config.tsOverrides for your machine, such as the dev proxyNo
.envDATABASE_URL, JWT keys, API_EXTERNAL_URLNo

What to run when something changes

ChangeLocalSelf-hosted
Schemasupatype pushsupatype push
FrontendNothing with the dev proxy. Otherwise npm run buildnpm run build, then compose render and compose up -d
supatype.config.tsRestart supatype devcompose render and compose up -d
.envRestart supatype devcompose up -d, or compose restart <service> for one service
ONE SERVICE

supatype self-host compose restart server recreates just that service with the current config and .env. Use it rather than typing a docker compose command yourself: the CLI renders the compose file first, so it always names this project's folders where they are now.

A typical server deploy

terminal
$ cd my-app
$ git pull
$ npm install           # if package.json changed
$ supatype push         # schema migrations
$ npm run build         # static files into public/ or dist/
$ supatype self-host compose render
$ supatype self-host compose up -d
NOTE

supatype self-host compose up points DATABASE_URL in .env at the Compose Postgres on SUPATYPE_DB_PORT (5432 unless you set it), so push and Studio use the same database as the stack. Leave it as it wrote it.

Upgrading Supatype

Moving to newer Supatype components is separate from deploying your own changes, and it takes two commands, not one.

terminal
$ supatype update      # pull new images and binaries
$ supatype self-host compose up -d   # run the new images
$ supatype push        # apply the schema those components expect

The push is the step that is easy to miss. Grants, policies, functions and buckets are generated from your schema and only reach the database through push, so new images on an older database can refuse rules until it runs. The upgrade is finished after the push, not before.

403S AFTER AN UPGRADE

This is the usual cause. The storage service logs the reason and names supatype push as the fix.

0.7.0

Upgrading from 0.6.0? Deploy the new realtime image before the first push, and upgrade the CLI with the engine. The upgrade notes cover ownership checks, declared renames, identity columns and the rest.
