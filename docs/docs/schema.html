Schema

Your schema is a set of TypeScript types in schema/index.ts. Supatype builds the tables, access rules, APIs and the typed client from it.

Pre-1.0: APIs and config may change between releases.

Models

Each exported Model<> type is a table. Import the types from @supatype/types.

Nothing in schema/index.ts runs. The CLI reads it as type declarations, so a model is an export type, never an export const, and there is no builder function to call.

schema/index.ts
import type { Model, UUID, Optional, Public, LoggedIn } from "@supatype/types"

export type Post = Model<{
  id: UUID
  title: string
  published: boolean
  published_at: Optional<string>
}, {
  access: { read: Public; create: LoggedIn; update: LoggedIn; delete: LoggedIn }
}>

The table name is the type name in snake case: Post becomes post, BlogPost becomes blog_post. Set tableName in the second argument to choose another.

An id: UUID field becomes the primary key, and the database fills it in. A model with no id field and no PrimaryKey<> gets one anyway: an id UUID primary key filled by gen_random_uuid(). Wrap another field in PrimaryKey<> to key the model by it instead.

The second argument also takes these options:

OptionDoes
label, labelPluralNames the model in Studio
indexesAdds indexes, see below
versionsKeeps drafts and history, see below
singleton: trueKeeps one row, such as site settings. The table is _global_ plus the snake case name, unless you set tableName
constraintsChecks the database runs on every write, in the access rule language, such as Lte<"starts_at", "ends_at">. They cannot name the caller or the clock
searchableThe fields the search box in Studio's list looks in
timestamps, softDeleteAdds created_at and updated_at columns, or a deleted_at column. Left out, they follow the fields the model declares
autoLocalize: trueMakes copy fields localized by default. Wrap one in NotLocalized<> to opt out
hooks, validateRuns an edge function before or after an API write, or to check one field. They do not run for direct SQL or seeds
cacheSays how reads of the model may be cached

An index is { fields: ["a", "b"] }, with unique: true and name if you need them. using picks the method: "btree" (the default), "gin", "gist", "hnsw" or "brin". An "hnsw" index is for Vector fields only. Its distance is "cosine" (the default), "l2" or "innerProduct". A distance on any other index is refused.

supatype dev applies each save. supatype push applies the schema to another database. supatype diff shows the change without applying it.

Field types

Every field is required (NOT NULL) unless you wrap it in Optional<>. Use Optional<>, not ?.

Wrap a field to add more:

WrapDoes
Unique<T>, Indexed<T>Adds a unique constraint, or an index
Default<T, value>Sets the column's default
ServerDefault<T>Says the database fills the column, by a trigger or default. Inserts may leave it out
MinLength<T, n>, MaxLength<T, n>Bounds the length of text
MinItems<T, n>, MaxItems<T, n>Bounds how many items an array, JSON array or Blocks field holds
Between<T, min, max>Bounds a number or a date
Searchable<T>Adds the field to the search box in Studio's list
Localized<T>Stores one value per locale, such as { "en": "Hello", "de": "Hallo" }

Three wrappers shape a field in Studio. EditorReadOnly<T> is shown but not editable there, and the API can still write it. Computed<T> is filled by the database and read-only in Studio. ComputedFrom<string, "title"> is prefilled from the fields it names on a new record, until the editor changes it.

For translated content, declare the locales once, such as export type Locales = LocaleConfig<["en", "fr"], "en">, and wrap a field in Localized<T>. It is stored as JSONB keyed by locale: { "en": "Hello", "fr": "Bonjour" }. LocalizedModel<> localizes a model's text fields for you, and NotLocalized<T> opts one back out. There is no locale setting in supatype.config.ts.

Wrap the fields in WithTimestamps<{ ... }> to add created_at and updated_at, which the database fills in.

With the Native provider, supatype dev stores Vector<> and Geo fields as JSONB, because its Postgres has no pgvector or PostGIS. Use Docker to work with them locally.

Identity and generated columns

An integer field can be an identity column. Int<{ identity: "always" }>, or Identity<number>, is GENERATED ALWAYS AS IDENTITY. An insert cannot give it a value. BigInt<{ identity: "by-default" }>, or Identity<bigint, "by-default">, takes a value when an insert gives one.

AutoIncrement<number> is Identity<number, "by-default">. Before 0.7.0 it was a SERIAL. A serial column pushed then is left as it is.

Generated<T, "sql"> is a stored generated column, such as Generated<string, "lower(name)">. Most types also take it as an option: Float<{ generated: "price * quantity" }>.

schema/index.ts
export type LineItem = Model<{
  id: PrimaryKey<Int<{ identity: "always" }>>
  price: Float
  quantity: Int
  total: Generated<Float, "price * quantity">
}>

A column cannot be both. Neither takes a Default<>. The generated client leaves generated columns and "always" identities out of inserts and updates. A "by-default" identity is optional on insert. Removing either is destructive, so the push asks first or needs --yes.

Relations

RelatedTo<Model> adds a foreign key column named after the field plus _id. The field author becomes the column author_id. The column can be null unless you pass { required: true }.

onDelete takes "cascade", "setNull", "restrict" or "noAction". It defaults to "restrict": deleting an author with posts is refused. onUpdate takes the same values and defaults to "cascade".

HasMany<Model> and HasOne<Model> are the other side of a RelatedTo. They add no column. They let the client and seeds reach the related rows.

ManyToMany<Model> makes one junction table for the pair, whichever side declares it. It is named from both tables in alphabetical order, so posts and tags share post_tag. Pass { through: "name" } to choose the name.

schema/index.ts
import type {
  Model, UUID, SupatypeAuthUserId, Timestamp, RichText, Slug, Unique, Optional, Int,
  RelatedTo, HasMany, ManyToMany, Owner, Role, LoggedIn, Public, Any, Lte, Now,
  Bucket, BucketPublic, BucketLoggedIn, BucketOwner, ImageAsset, Block, Blocks, Default,
} from "@supatype/types"

export type Author = Model<{
  id: SupatypeAuthUserId
  name: string
  bio: Optional<string>
  posts: HasMany<Post>
}, {
  access: { read: Public; create: Owner<"id">; update: Owner<"id">; delete: Owner<"id"> }
}>

export type Tag = Model<{
  id: UUID
  name: Unique<string>
}, {
  access: { read: Public; create: Role<"admin">; update: Role<"admin">; delete: Role<"admin"> }
}>

export type Post = Model<{
  id: UUID
  title: string
  slug: Unique<Slug<"title">>
  body: RichText
  sections: Optional<Blocks<HeroBlock | ProseBlock>>
  kind: "news" | "guide"
  cover: Optional<ImageAsset<Covers>>
  author: RelatedTo<Author, { required: true; onDelete: "cascade" }>
  tags: ManyToMany<Tag>
  comments: HasMany<Comment>
  views: Default<Int, 0>
  published_at: Optional<Timestamp>
}, {
  versions: { drafts: true }
  access: {
    read: Any<[Lte<"published_at", Now>, Owner<"author_id">]>
    create: Owner<"author_id">
    update: Owner<"author_id">
    delete: Any<[Owner<"author_id">, Role<"admin">]>
  }
}>

export type Comment = Model<{
  id: UUID
  post: RelatedTo<Post, { required: true; onDelete: "cascade" }>
  user_id: SupatypeAuthUserId<{ onDelete: "cascade" }>
  body: string
}, {
  access: { read: Public; create: Owner<"user_id">; update: Owner<"user_id">; delete: Owner<"user_id"> }
}>

The other pages use this schema in their examples. HeroBlock, ProseBlock and Covers are defined further down.

Access rules

Each model has a rule for read, create, update and delete. The rules become Postgres row level security, so they hold for REST, GraphQL, realtime and the client alike.

An operation with no rule is denied. A model with no access at all is not reachable through the API.

RuleWho passes
PublicEveryone, signed in or not
LoggedInAny signed-in user
PrivateNobody through the API
Owner<"author_id">The user whose id is in that column. Use "id", a SupatypeAuthUserId field, or a relation's _id column. Owner<Post, "author_id"> also names the model, so the editor checks the field
OwnerFrom<"post">The owner of the related row, one relation deep
Role<"admin">A user whose app_metadata.role is admin
Any<[A, B]>, All<[A, B]>, Not<A>Either rule, both rules, or the opposite
Eq, Neq, Gt, Gte, Lt, Lte, LikeA comparison, such as Lte<"published_at", Now>
In<"site_id", Rows<"user_sites", "site_id", Eq<"user_id", AuthUid>>>The column's value is in the set: rows of another table, Values<["draft", "review"]>, or a claim holding an array
Exists<Rows<...>>The set is not empty, whatever the row holds

In a comparison, a plain string names a column. Wrap a constant in Literal<>. Now, AuthUid and Claim<"app_metadata.plan"> are also available. IsNull<"col"> and NotNull<"col"> test for null.

A time can be relative to now. Ago<30, "days"> and FromNow<7, "days"> take one amount and one unit. StartOf<"day"> is the start of the day, week, month or year. After<Now, { days: 30 }> and Before<StartOf<"day">, { hours: 9 }> add or take away several units at once. So Gte<"created_at", Ago<30, "days">> passes rows from the last 30 days.

Since 0.7.0 a push refuses an owner rule that could never match. An Owner on a relation must reach, through one relation at most, a model keyed by a SupatypeAuthUserId or one with its own Owner rule. On a plain UUID field it still works, with a warning.

Role<> reads the user's app_metadata.role, which only the auth admin API can set. It is not the Studio role.

Field rules and masking

A field rule limits who can read or write one column. Declare it under access.fields.

schema/index.ts
export type Profile = Model<{
  id: SupatypeAuthUserId
  display_name: string
  email: string
}, {
  access: {
    read: Public
    create: Owner<"id">
    update: Owner<"id">
    delete: Owner<"id">
    fields: { email: { read: Any<[Owner<"id">, Role<"moderator">]>; write: Owner<"id"> } }
  }
}>

A caller who may not read the column still gets the row, with the value masked as null. A write the rule refuses fails with error 42501.

Name a relation by its column, such as author_id.

NOT WITH VERSIONS

A model with versions cannot have field rules. Old versions are stored as JSON snapshots, where a column rule cannot be enforced. The schema is refused and the message asks you to drop one of the two.

Auth user ids

SupatypeAuthUserId holds the id of a sign-in user. Use it for owner columns.

When the create rule is Owner<"col"> and the column has no default, the column defaults to the caller's own user id. So a client can leave it out on insert.

By default there is no foreign key to the user. Deleting a user leaves their rows as they were. Add onDelete to get one:

onDeleteWhen the user is deleted
"cascade"Their rows are deleted too
"restrict"Deleting the user is refused while they own rows
"setNull"The column is set to null. The field must be Optional<>

The push that adds the key refuses if existing rows name a user that does not exist. Its message says how many rows and how to remove them. It also refuses if the database has no auth.users table, which Supatype's auth server creates. Start the auth server against the database once, or remove onDelete so the field holds an id with no foreign key.

Drafts and versions

versions: { drafts: true } keeps drafts and a history of each record. versions: true is short for the same. keep sets how many versions to keep (default 20).

The model's own table holds the published record. That is what read rules and the public API see. Drafts and old versions live in post_versions.

Publishing copies a draft into the live table. It also sets published_at if it is empty. The update rule decides who may publish.

A direct API update of the live row is refused with error 42501. Save a draft with the client's update, then publish, or pass { publish: true } to do both. See Client.

versions: { drafts: false } keeps history only. Writes go straight to the live row.

The read rule does not decide who sees a draft. The record's creator sees it. So do the Studio roles in publishing.draft_visibility in supatype.config.ts (default admin, developer and editor), and anyone with a signed preview link.

Slugs, rich text and blocks

Slug<"title"> fills itself from title when you leave it empty. While it still holds the generated value, it follows the title when the title changes. Set it yourself to keep a URL fixed. Add Unique<> if it must be unique.

RichText stores a rich text document. When you write, a plain string is accepted and becomes one paragraph. A read always returns the document.

Blocks<T> is a list of sections an editor arranges in Studio. Each block is Block<"name", { fields }>:

schema/index.ts
export type HeroBlock = Block<"hero", { heading: string; image: Optional<ImageAsset<Covers>> }>
export type ProseBlock = Block<"prose", { body: RichText }>

Each entry is stored as { "type": "hero", "data": { "heading": "Hi" } }. A renderer switches on type and reads data. Rich text inside a block is not converted from a string, so write the full document there.

A third argument, { label, icon }, sets how Studio shows the block, such as Block<"hero", { heading: string }, { label: "Hero banner" }>. Both are optional.

Before 0.7.0 a block's fields sat beside type. supatype push moves entries stored that way under data, and supatype diff shows how many are pending. Push before anyone opens those records in Studio. See Upgrading.

Storage buckets

schema/index.ts
export type Covers = Bucket<"covers", {
  accessMode: "public"
  accept: ["image/png", "image/jpeg", "image/webp"]
  maxSize: "5MB"
  access: { read: BucketPublic; create: BucketLoggedIn; update: BucketOwner; delete: BucketOwner }
}>

A bucket has the same four rules as a model. update means overwriting a file. The rules are BucketPublic, BucketLoggedIn, BucketOwner (the uploader), BucketRole<"name"> and BucketPrivate.

A rule you leave out is refused for everyone but the service role, and the push warns about it. accessMode: "public" serves files on a public URL whatever read says.

ImageAsset<Covers> on a model stores a reference to a file in that bucket.

Renames

A push never guesses a rename. Renaming a field in the schema looks like a drop and an add.

In a terminal, supatype push and supatype dev ask, for example "Was post.title renamed to post.headline? (recorded in supatype/renames.json)". Answer yes and it records the rename. Without a terminal the push stops and prints the supatype rename command to run.

terminal
$ supatype rename post.title post.headline   # a column
$ supatype rename post article               # a table

Renames are recorded in supatype/renames.json. Commit it. Every push replays it, so each database gets the same rename. supatype rename --prune removes entries the target database has already applied. Point it at a database with --connection, --env or --direct, as for a push.

CAREFUL

supatype push --yes does not ask about renames. An unrecorded rename is then pushed as a drop and an add, and the column's data is lost. Record renames first.

What a push refuses

Push stops whenTo go on
A change can lose data, such as a dropAnswer yes in a terminal, or pass --yes in CI
A table the schema names exists but Supatype did not create itsupatype adopt, or give the model another tableName. The push offers to adopt in a terminal
A change rewrites or scans a table of more than 100,000 rows, which locks it while it runsAnswer yes in a terminal, or pass --yes
Policies, grants, labels or row level security were changed outside Supatype--overwrite-drift puts Supatype's back. To keep the hand edits, run supatype doctor --rebaseline --accept-access-drift

An onDelete key would point at missing usersDelete or fix those rows
An onDelete key needs auth.users and the database has noneStart the auth server against the database once, or remove onDelete
The schema has identity or generated columns and the engine is older than 0.7.0Run supatype update
A JSON field changed to Blocks holds values that are not objectsChange or remove those values, then push again

--yes does not override hand-edited access rules. Only --overwrite-drift does. Objects that Supatype did not create are never dropped or taken over.
