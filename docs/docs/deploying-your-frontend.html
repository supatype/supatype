Deploy your frontend

A production build of your app needs two values: your deployment's API URL and its anon key. This page shows how each host gets them, and what you see when one is missing.

Pre-1.0: APIs and config may change between releases.

What a build needs

supatype init, supatype dev and supatype keys write a local stack's URL and anon key to .env.development.local. Vite, Next.js and Expo read that file in development only, so a production build never ships localhost, and gets neither value from it. A production build gets them in one of three ways:

WayUse it when
supatype buildYou run the build command, on any host. It gives the build both values under every framework's name, and refuses to start without them.
supatype keys --print frontendYou paste the values into a host's settings. It prints each name and value as a NAME=value line.
<script src="/supatype-env.js" vite-ignore>Supatype serves the app, or it is a Next.js app with the route below. The page reads both values from the server when it loads, so one build runs on every deployment that serves it.

Each framework reads its own names. supatype build and keys --print frontend give all of them:

FrameworkAPI URLAnon key
ViteVITE_SUPATYPE_URLVITE_SUPATYPE_ANON_KEY
SvelteKit, AstroPUBLIC_SUPATYPE_URLPUBLIC_SUPATYPE_ANON_KEY
Next.jsNEXT_PUBLIC_SUPATYPE_URLNEXT_PUBLIC_SUPATYPE_ANON_KEY
ExpoEXPO_PUBLIC_SUPATYPE_URLEXPO_PUBLIC_SUPATYPE_ANON_KEY

Pass the values straight to createClient, as Client: Create the client does, with no check of your own in front of it. A bundler that knows a name is unset can turn such a check into a throw that hides the reason. The client checks for itself, and names what is missing.

supatype build

terminal
$ supatype build                                # runs the package.json build script
$ supatype build -- vite build                  # or the command after --
$ supatype build --env staging -- npm run build # for one linked environment

Keep the real build command, such as vite build, in package.json's build script. A build script that is itself supatype build is refused, since a bare supatype build runs that script: it stops and says the build script calls supatype build itself, so running it again would never end. A command after -- runs even inside another build.

It runs your build with the deployment's API URL and anon key under all four prefixes. It writes no file: the values live only in the build's environment. The exit code is the build's own, so CI behaves as it did before. Each value is looked for on its own, in this order:

SourceWhere it looks
The environmentSUPATYPE_URL and SUPATYPE_ANON_KEY, or any of the names above. A host's own settings always win.
The server the URL namesFor the anon key only, when the environment holds a URL: <URL>/supatype-env.json, the key that server publishes. HTTPS for an address that is not local, a local one only with --allow-local. A 503 there reads the server at <url> is not set up to publish its anon key: and the setting the server names.
The linked environmentThe one --env names, else the link's default. Supatype Cloud: the environment's address, and its anon key from the control plane, which needs supatype login (or SUPATYPE_ACCESS_TOKEN) as an owner or admin. Self-host: the link's address, and the anon key the server publishes at /supatype-env.json, fetched only over HTTPS for an address that is not local.
.envPUBLIC_SUPATYPE_URL or API_EXTERNAL_URL, and ANON_KEY, as the server's own .env holds them.

The first source holding a value decides it. A local address there, such as localhost or 127.0.0.1, stops the build rather than being passed over, because a production build would ship it. Pass --allow-local to build against a local stack anyway. A service role key offered as the anon key stops the build too: the service role key never reaches a build. An anon key counts only for the URL being built for: with SUPATYPE_URL naming one deployment and a link to another, the link's key is listed as skipped ... not the URL being built for, never paired with the wrong address.

.supatype/link.json holds secrets and is never committed, so a CI host has no link. There, set SUPATYPE_URL in the host's settings: supatype build fetches the anon key from <SUPATYPE_URL>/supatype-env.json, copies both to every framework's names, and stops the build when one is missing. Set SUPATYPE_ANON_KEY as well only when that server does not publish it (server.public_env: false, or a plain http:// address). supatype deploy builds your app with the same values, and takes --allow-local too.

Supatype hosts it

When a self-hosted stack serves your app (app.mode: "static"), its server answers /supatype-env.js with its own address and anon key:

terminal
$ curl https://example.com/supatype-env.js
window.__SUPATYPE_ENV__ = {"url":"https://example.com","anonKey":"eyJhbGciOi..."};

supatype init puts the tag in a static app's index.html, in the head, so it runs before the app's own script. For an app made another way, add it yourself:

index.html
<script src="/supatype-env.js" vite-ignore></script>

vite-ignore tells Vite to leave the tag as it is. The project has no such file, since the server answers it, so without the attribute every vite build warns <script src="/supatype-env.js"> in "/index.html" can't be bundled without type="module" attribute. Vite drops the attribute from the page it builds, and a browser ignores it, so the same tag does for a page with no build step. Do not make it type="module": Vite then tries to bundle it, and the build fails with Failed to resolve /supatype-env.js.

The client reads window.__SUPATYPE_ENV__ for any value the build did not carry, at its first request. It never guesses the address from the page. A value the build did carry always wins. So a build made with neither value, by a plain npm run build, runs on every deployment that serves it. Served from the API's own origin, it needs no allowed origin either. To build on the server instead:

vm
$ supatype app add --static ./dist   # once, then commit supatype.config.ts
$ supatype build                     # reads API_EXTERNAL_URL and ANON_KEY from .env
$ supatype self-host compose up -d
IF THE KEY IS MISSING

supatype build stops before the build starts and lists every source it tried, as shown in When a value is missing. A page built without the key and served without the script tag, or by a server with server.public_env: false, makes its first request throw in the browser console: Supatype client has no anon key.

CLOUD

For Supatype Cloud, supatype build --env <name> and supatype deploy read the environment's anon key from the control plane, so a build on a linked machine needs nothing set by hand. Each Cloud environment's API also answers /supatype-env.json and /supatype-env.js on its own address. On a CI host, use the sections below.

Next.js

A Next.js app does not need its values at build time. next build prerenders pages without them, and the route app/supatype-env.js/route.ts serves them to each page load from SUPATYPE_URL and SUPATYPE_ANON_KEY in the server's environment. createServerClient reads the same two, for Server Components, Route Handlers and middleware. supatype init writes the route and the root layout's script for an App Router app; Frameworks: Next.js shows both, and the server client. So one build runs on every environment: set the two variables where the app runs. In development the route answers too: supatype dev, init and keys --write put the local stack's SUPATYPE_URL and SUPATYPE_ANON_KEY in .env.development.local, which next dev reads.

HostWhat to set
VercelSUPATYPE_URL and SUPATYPE_ANON_KEY under the project's Environment Variables, for each environment. The build command stays next build.
NetlifyThe same two, under the site's Environment variables.
Your own Node serverThe same two, in the environment of the process that runs next start.
vm
$ npm run build
$ SUPATYPE_URL=https://api.example.com SUPATYPE_ANON_KEY=eyJhbGciOi... npm start

supatype keys --print frontend prints the values to copy. The route is read on every page load and the server client on every call, so the same build started with another deployment's two values runs against that one. A value fixed into the build under NEXT_PUBLIC_SUPATYPE_URL or NEXT_PUBLIC_SUPATYPE_ANON_KEY still wins over the route's, so leave those unset in production. A Next.js app on its own host or server is on another origin from the API: add its address to the API's allowed origins, as in Allow your app's origin. The server client uses them only where SUPATYPE_URL or SUPATYPE_ANON_KEY is unset.

A static export (output: "export" in next.config) has no server to run the route, so init writes no route, no layout script and no @supatype/ssr for it, and prints the two ways instead: build with the values, supatype build -- next build, or have Supatype host the export (supatype app add --static ./out), whose server answers /supatype-env.js itself; add the <Script> tag to the root layout for that.

A Pages Router app gets nothing written by init, which prints these steps instead: create the same route file under app/supatype-env.js/, beside pages/; in pages/_document.tsx, import Script from next/script and put <Script src="/supatype-env.js" strategy="beforeInteractive" /> inside <Head>; add @supatype/ssr to the app's dependencies, and set the two variables where it runs.

IF THE KEY IS MISSING

The build still succeeds, and the page renders. With SUPATYPE_ANON_KEY or SUPATYPE_URL unset, /supatype-env.js answers 503, not cached, naming the variable: public env unavailable: SUPATYPE_ANON_KEY is not set on this server. It answers 503 too when SUPATYPE_ANON_KEY holds a service role key, and 404 only when SUPATYPE_PUBLIC_ENV is off. The browser client's first request then throws Supatype client has no API address and anon key. createClient was given none, and the page had set no window.__SUPATYPE_ENV__ by its first request., naming the route and the two variables. A server client given neither throws on its first request: Supatype client has no API address and anon key. It was given none, and it is running on a server, where there is no page to read them from., followed by Set SUPATYPE_URL and SUPATYPE_ANON_KEY in the server's environment.

Vercel

Print the values for the deployment on your own machine, where the project is linked:

terminal
$ supatype keys --print frontend --env production
VITE_SUPATYPE_URL=https://api.example.com
PUBLIC_SUPATYPE_URL=https://api.example.com
NEXT_PUBLIC_SUPATYPE_URL=https://api.example.com
EXPO_PUBLIC_SUPATYPE_URL=https://api.example.com
VITE_SUPATYPE_ANON_KEY=eyJhbGciOi...
PUBLIC_SUPATYPE_ANON_KEY=eyJhbGciOi...
NEXT_PUBLIC_SUPATYPE_ANON_KEY=eyJhbGciOi...
EXPO_PUBLIC_SUPATYPE_ANON_KEY=eyJhbGciOi...

In the Vercel project's settings, under Environment Variables, add SUPATYPE_URL with that value, for each environment you deploy. supatype build fetches the anon key from the server it names; add SUPATYPE_ANON_KEY too if that server does not publish it. Then have Vercel build through the wrapper:

vercel.json
{
  "buildCommand": "npx supatype build"
}

supatype build copies the two values to NEXT_PUBLIC_, VITE_ and the other names, then runs your build script. A Next.js app needs no wrapper on Vercel: see Next.js.

Then allow the site on the API: add its *.vercel.app address and any custom domain to the allowed origins, as in Allow your app's origin.

IF THE KEY IS MISSING

The deployment fails at its build step, before your build starts. The build log shows No anon key for a production build of the front end., each source tried, and ends or set SUPATYPE_ANON_KEY.

Netlify

Under the site's configuration, in Environment variables, add SUPATYPE_URL, and SUPATYPE_ANON_KEY only if the server does not publish its key, with the values supatype keys --print frontend prints. Then set the build command:

netlify.toml
[build]
  command = "npx supatype build"
  publish = "dist"

publish is your build's output directory: dist for Vite, build for SvelteKit's static adapter. Then add the site's *.netlify.app address and any custom domain to the API's allowed origins, as in Allow your app's origin.

IF THE KEY IS MISSING

The deploy fails in its build step with the same refusal, and nothing is published: the site keeps serving the last deploy that built.

Cloudflare Pages

In the Pages project's settings:

SettingValue
Build commandnpx supatype build
Build output directoryYour build's output, such as dist
Variables and SecretsSUPATYPE_URL, from supatype keys --print frontend, and SUPATYPE_ANON_KEY only if the server does not publish its key

Then add the project's *.pages.dev address and any custom domain to the API's allowed origins, as in Allow your app's origin.

IF THE KEY IS MISSING

The build fails, and its log shows the refusal with each source tried. A variable added after the last build reaches only the next one, so retry the deployment once it is set.

GitHub Actions

Store SUPATYPE_URL as a repository variable, under Settings, Secrets and variables, Actions. supatype build fetches the anon key from the server it names, so a self-hosted deployment needs nothing more: no link and no service role key in CI. Where the server does not publish the key, store SUPATYPE_ANON_KEY too; it is public, so a variable, not a secret, will do.

.github/workflows/build.yml
name: Build

on:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npm ci
      - run: npx supatype build
        env:
          SUPATYPE_URL: ${{ vars.SUPATYPE_URL }}
          # Only where the server does not publish its key:
          # SUPATYPE_ANON_KEY: ${{ vars.SUPATYPE_ANON_KEY }}

Publish the output however you deploy it, and add the address it is served from to the API's allowed origins (Allow your app's origin). To give every later step the values under every framework's name instead, run npx supatype keys --print frontend >> "$GITHUB_ENV" with the same env:. To deploy to your own server over SSH and build there, follow Deploy to a VM with GitHub Actions.

IF THE KEY IS MISSING

The npx supatype build step fails and the job stops there. A variable that does not exist reaches the step as an empty string, which counts as not set.

Your own server

On the server that runs the stack, supatype build needs nothing more: its .env records the deployment's API_EXTERNAL_URL and ANON_KEY.

vm
$ cd /opt/my-app
$ git pull
$ npm install
$ supatype push
$ supatype build
$ supatype self-host compose up -d

To build somewhere else, such as your laptop, set SUPATYPE_URL to the deployment's address, or link the deployment and name it:

terminal
$ supatype link --env production --url https://api.example.com --token "$SERVICE_ROLE_KEY"
$ supatype build --env production

Then copy the output to whatever serves it, and add that server's address to the API's allowed origins (Allow your app's origin); built on the stack's own server and served by it, the app needs nothing. For a self-hosted link the anon key comes from https://api.example.com/supatype-env.json. It is fetched over HTTPS only, so a link to a plain http:// address that is not local gives no key; set SUPATYPE_ANON_KEY instead. A Supatype Cloud link reads the key from the control plane.

IF THE KEY IS MISSING

On the server, anon key from .env: no ANON_KEY means the keys were never made: run supatype keys. is a local address, which a production build would ship means API_EXTERNAL_URL in .env is still a localhost address: set it to the server's public one.

Allow your app's origin

A self-hosted API answers browsers only from the origin of its SITE_URL and the origins you list. An app served from anywhere else, such as Vercel, Netlify, Cloudflare Pages, a Next.js server of its own or a dev server on another port, is refused: the preflight gets 403, and the browser reports Failed to fetch. When Supatype serves the app, it is on the API's own origin and needs nothing here.

List the app's origin in supatype.config.ts, or in .env as SUPATYPE_CORS_ALLOW_ORIGINS, comma-separated. Each entry is scheme://host[:port], with no path:

supatype.config.ts
// supatype.config.ts (excerpt)
api: { corsOrigins: ["https://my-app.vercel.app", "https://www.example.com"] },
.env
SUPATYPE_CORS_ALLOW_ORIGINS=https://my-app.vercel.app,https://www.example.com
vm
$ supatype self-host compose restart server

The restart renders the compose file again and recreates the server with the new list. Owners, admins and developers can instead add the origin in Studio, on the Settings page's CORS tab, which needs no restart; a list saved there replaces the default until it is reset, and the site URL stays allowed whatever is saved. On Supatype Cloud, add it there. Each preview deployment with its own address is another origin. supatype dev allows every origin, so a local stack never shows this. The rest of the rules are under Self-hosting, in Allowed origins.

When a value is missing

At build time, supatype build stops before the build starts, exits 1, and lists every source it tried for each value. With nothing set, in a project that is not linked:

terminal
$ supatype build
✗ No API URL and no anon key for a production build of the front end.
  not set  API URL from the environment: none of SUPATYPE_URL, VITE_SUPATYPE_URL, PUBLIC_SUPATYPE_URL, NEXT_PUBLIC_SUPATYPE_URL, EXPO_PUBLIC_SUPATYPE_URL is set
  not set  anon key from the environment: none of SUPATYPE_ANON_KEY, VITE_SUPATYPE_ANON_KEY, PUBLIC_SUPATYPE_ANON_KEY, NEXT_PUBLIC_SUPATYPE_ANON_KEY, EXPO_PUBLIC_SUPATYPE_ANON_KEY is set
  not set  anon key from the server SUPATYPE_URL names: no API URL in the environment to ask
  not set  API URL from the linked environment: no .supatype/link.json (run `supatype link`)
  not set  anon key from the linked environment: no .supatype/link.json (run `supatype link`)
  not set  API URL from .env: no PUBLIC_SUPATYPE_URL or API_EXTERNAL_URL
  not set  anon key from .env: no ANON_KEY

Run `supatype build --env <name>` for a linked deployment, or set SUPATYPE_URL and SUPATYPE_ANON_KEY.

The first line starts with ✗ in a terminal, and with [supatype] in a CI log or anywhere else the output is not a terminal. With SUPATYPE_URL set it starts No anon key for a production build of the front end., and the line for the server the URL names says what that server answered.

supatype keys --print frontend reads the same sources, refuses the same way, and names itself as the command to run. It takes --allow-local too, for printing a local stack's values: supatype keys --print frontend --allow-local. At run time, creating the client never throws, so next build can prerender a page that creates one at module scope. The first request a client makes without the anon key throws a MissingClientValuesError instead, so the browser console says what is wrong rather than the page going blank. The error starts Supatype client has no anon key. createClient was given none, and the page had set no window.__SUPATYPE_ENV__ by its first request. and goes on to name the build-time variables, supatype build, the script tag, and for Next.js the route and the server's SUPATYPE_URL and SUPATYPE_ANON_KEY. With no address either, it starts Supatype client has no API address and anon key.

The anon key is public

The anon key is not a secret. Every browser that loads your app holds it, which is why the server can publish it and a CI host can keep it as a plain variable. What protects your data is the access rules in your schema, which every request made with the anon key goes through.

The service role key passes every rule, so it never goes near a build. supatype build and keys --print frontend never output it, and refuse a service role key offered as the anon key. The server never serves it.

/supatype-env.json and /supatype-env.js are on by default. For an API-only project, with no frontend for the server to serve, turn them off:

supatype.config.ts
// supatype.config.ts (excerpt)
server: {
  public_env: false,
},

The next supatype self-host compose up -d gives the server SUPATYPE_PUBLIC_ENV=false, and both addresses answer 404. A deployment that means to publish and cannot (no anon key, no URL, or a service role key in SUPATYPE_ANON_KEY) answers 503 instead, with no caching and a body naming the setting to fix. supatype dev does the same. Turning them off does not make the anon key secret: every client of the API still holds it. It only stops the server publishing it, and supatype build for that deployment then needs SUPATYPE_ANON_KEY set.
