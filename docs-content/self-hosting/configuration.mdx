---
title: Configuration
description: Environment variables and configuration options for self-hosted Supatype deployments.
---

A self-hosted stack reads its settings from two places: `supatype.config.ts`, and `.env` in the
project root. Every `supatype self-host compose` command renders
`.supatype/self-host/docker-compose.yml` from both, and Compose substitutes the `.env` values into
it. Most containers see only the variables the generated file names. The one exception is the
`server` container: it mounts the project at `/project` and loads `.env` itself, without
overriding a value Compose already set, so an auth server setting such as
`SUPATYPE_EXTERNAL_ANONYMOUS_USERS_ENABLED` also takes effect there. The services' internal settings (ports between
containers, PostgREST's roles, the object store's credentials) are fixed in the generated file.

Variables marked **Required** have no default: Compose stops before starting anything and names the
one that is missing, for example `POSTGRES_PASSWORD is missing from .env`.

## Database

| Variable | Default | Description |
|----------|---------|-------------|
| `POSTGRES_PASSWORD` | None | **Required.** Password of the database's superuser, for direct SQL access |
| `POSTGRES_USER` | `supatype_admin` | The superuser. The bundled `supatype/postgres` image runs as `supatype_admin`, and the CLI refuses any other value |
| `POSTGRES_DB` | `supatype` | Database name. `supatype init` sets it to the project name |
| `AUTHENTICATOR_PASSWORD` | None | **Required.** Password of `authenticator`, the role PostgREST connects as. Keep it different from `POSTGRES_PASSWORD`, so rotating yours does not take the REST API down |
| `SUPATYPE_SQL_EDITOR_PASSWORD` | None | **Required.** Password of `supatype_sql_editor`, the role Studio's SQL editor connects as. It is not a superuser |
| `DATABASE_URL` | None | The connection string the CLI uses from the host. With [`database.external`](/docs/self-hosting/external-database.html) every service uses it too, and it becomes required |
| `SUPATYPE_DB_PORT` | `5432` | Host port the database is published on |
| `SUPATYPE_DB_PUBLIC_HOST` | `server.domain`, else `127.0.0.1` | Host name Studio shows in the database's connection strings |
| `SUPATYPE_DB_POOLER_URL` | None | A connection pooler's URL, for Studio to show beside the direct one |
| `SUPATYPE_ALLOW_SECRET_READBACK` | `false` | Lets Studio reveal the database password through the server's admin routes |

`supatype init` generates `POSTGRES_PASSWORD`, `AUTHENTICATOR_PASSWORD` and
`SUPATYPE_SQL_EDITOR_PASSWORD` for a new project.

## Keys and secrets

| Variable | Default | Description |
|----------|---------|-------------|
| `JWT_SECRET` | None | **Required.** Signs every token. At least 32 characters: see [JWT secret length](#jwt-secret-length) |
| `ANON_KEY` | None | The public API key, a JWT signed with `JWT_SECRET`. `supatype self-host compose up` mints it when it is blank |
| `SERVICE_ROLE_KEY` | None | The admin API key, minted the same way. Required by the control plane |
| `SUPATYPE_CONTROL_PLANE_SECRET` | Generated | Shared by the API server and the control plane only. Every `self-host compose` command writes one into `.env` when it is missing |
| `SUPATYPE_KEYSPACE_PASSWORD` | Generated | The cache's password, required when the cache runs inside Postgres on `supatype/postgres` 17.2.13 or later. Generated the same way. See [Cache](#cache) |

Access tokens expire after 3600 seconds. The generated file fixes this value; `.env` does not
change it.

### JWT secret length

PostgREST refuses to start with a JWT secret shorter than 32 characters, and everything else in the
stack accepts one, so a short secret used to bring the stack up whole except for the REST API. The
CLI now checks first: `supatype dev` and `supatype self-host compose up` stop before starting
anything when `JWT_SECRET` is too short, with:

```
JWT_SECRET in .env is 20 characters, and the REST API needs at least 32.
```

Generate a longer one, for example with `openssl rand -base64 48`, put it in `.env` as `JWT_SECRET`,
then run `supatype keys --write --force` to sign `ANON_KEY` and `SERVICE_ROLE_KEY` with it. Without
`--force`, `--write` only fills keys that are blank and leaves keys signed with the old secret in
place.

## Public URLs and ports

| Variable | Default | Description |
|----------|---------|-------------|
| `API_EXTERNAL_URL` | `http://localhost:18473`, or `https://<server.domain>` with TLS on | The API's public address. Emailed links, OAuth redirect URIs and `ctx.publicUrl` in functions are built from it |
| `SITE_URL` | `http://localhost:3000`, or `https://<server.domain>` with TLS on | Your application's URL, for auth redirects. Its origin is always allowed by CORS |
| `SUPATYPE_KONG_PORT` | `18473` | Host port of the gateway. With TLS on, the gateway publishes ports 80 and 443 instead |
| `SUPATYPE_SERVER_PORT` | `9999` | Host port of the API server itself, behind the gateway |
| `SUPATYPE_SEAWEEDFS_PORT` | `8333` | Host port of the object store behind storage. Unused with `storage.production: "s3"`, which runs none ([Storage](#storage)) |
| `SUPATYPE_PUBLISH_ADDRESS` | `127.0.0.1` | Address the database, the API server and the object store are published on. Loopback keeps them off the network; the gateway is the way in |

TLS is on when `supatype.config.ts` sets `server.mode: "standalone"`, a `server.domain` and
`server.tls.email`. See [Docker setup](/docs/self-hosting/docker.html#step-4-set-up-https).

## Authentication

| Variable | Default | Description |
|----------|---------|-------------|
| `DISABLE_SIGNUP` | `false` | Refuse new sign-ups |
| `SUPATYPE_EXTERNAL_EMAIL_ENABLED` | `true`, or `false` when `auth.email.enabled` is `false` | Email-and-password sign-up and sign-in, with magic links and password recovery |
| `SUPATYPE_MAILER_AUTOCONFIRM` | `false`, or `true` when `auth.email.enableConfirmations` is `false` | Confirm new email addresses without sending a confirmation email |

The defaults come from `auth.email` in `supatype.config.ts`, and either variable set in `.env` wins
over the config (restart the stack after changing it). The CLI never writes them into `.env`; a
`SUPATYPE_MAILER_AUTOCONFIRM` line an earlier CLI wrote there is taken out on the next start, with a
message saying so. A self-hosted stack sends a confirmation link with every new email sign-up
unless one of them says otherwise, so configure email delivery (below) before you open sign-up.
Local dev confirms sign-ups at once unless the config says otherwise.

### Email

| Variable | Default | Description |
|----------|---------|-------------|
| `SUPATYPE_MAILER_MAILER_PROVIDER` | `console` | `console` writes each message to the server's log and sends nothing. Set `smtp` to deliver through the server below |
| `SUPATYPE_SMTP_HOST` | None | SMTP server hostname |
| `SUPATYPE_SMTP_PORT` | `587` | SMTP server port |
| `SUPATYPE_SMTP_USER` | None | SMTP username |
| `SUPATYPE_SMTP_PASS` | None | SMTP password |
| `SUPATYPE_SMTP_ADMIN_EMAIL` | None | The address messages are sent from |
| `SUPATYPE_SMTP_SENDER_NAME` | None | The name shown beside that address |

With the default provider no email leaves the server, whatever the SMTP variables say. The generated
file passes only these settings, so on a self-hosted stack use `console` or `smtp`.

### OAuth providers

Declare providers under `auth.providers` in `supatype.config.ts`. The compose file turns each one
into the `SUPATYPE_EXTERNAL_<PROVIDER>_*` variables the auth server reads, and fills in the redirect
URI as `API_EXTERNAL_URL` followed by `/auth/v1/callback`:

```typescript
// docs:no-check (a fragment: the rest of your config stays as it is)
import { defineConfig, env } from "@supatype/cli"

export default defineConfig({
  auth: {
    providers: {
      github: { clientId: "Iv1.0123456789abcdef", secret: env("GITHUB_SECRET") },
    },
  },
})
```

The secret is the name of a variable in `.env`, never the value. For each declared provider, a
`SUPATYPE_EXTERNAL_<PROVIDER>_<SETTING>` variable in `.env` (`_ENABLED`, `_CLIENT_ID`, `_SECRET`,
`_REDIRECT_URI`, `_URL`, `_SKIP_NONCE_CHECK`, `_EMAIL_OPTIONAL`) overrides what the config gives.
A provider that is not under `auth.providers` does not reach the server, even when its variables are
in `.env`. See [OAuth providers](/docs/auth/oauth.html).

## Allowed browser origins (CORS)

Outside dev mode the server's gateway decides CORS for every service behind it. The browser origins
it allows by default are:

1. the origin of `SITE_URL`,
2. the origins in `api.corsOrigins` in `supatype.config.ts`,
3. the origins in `SUPATYPE_CORS_ALLOW_ORIGINS` in `.env` (comma-separated).

```typescript
// docs:no-check (a fragment: the rest of your config stays as it is)
// supatype.config.ts
import { defineConfig } from "@supatype/cli"

export default defineConfig({
  project: { name: "my-project" },
  server: { mode: "standalone" },
  api: { corsOrigins: ["https://admin.example.com", "http://localhost:5173"] },
})
```

Each `api.corsOrigins` entry is `scheme://host[:port]` with an `http` or `https` scheme, or `*`.
Anything else (a path, a query, another scheme) stops the config from loading with
`api.corsOrigins must be an array of origins (scheme://host[:port]) or "*"`. The generated compose
file passes the config's origins to the server ahead of `SUPATYPE_CORS_ALLOW_ORIGINS`, so
re-render it (any `supatype self-host compose` command does) after changing them.

Owners, admins and developers can also change the list in Studio, on the **Settings > CORS** tab,
which shows each origin and where it comes from. A list saved there is kept in the project's
database (`auth.cors_origins`), survives a restart, reaches every server replica within ten
seconds, and replaces the default until someone presses **Reset to default**. Viewers can read it.

| | |
|---|---|
| Site URL | Always allowed, whatever list is saved |
| Any other origin | Refused: a preflight gets `403`, and other responses carry no CORS headers |
| `*` | Allows every origin, and only when you write it in one of the places above. It is never a default |
| Dev mode | Unchanged: `supatype dev` allows every origin, whatever the list says |

Before this, a standalone server with no `SUPATYPE_CORS_ALLOW_ORIGINS` allowed every origin. If a
production web app on another origin calls your API, add its origin before upgrading.

## Cache

The API server's response cache, and the gateway's certificates once HTTPS is on, are kept in a
keyspace that speaks the Redis protocol (RESP). It is
[pg_keyspace](/postgres/pg-keyspace.html) inside the `db` container, unless `cache.provider` in
`supatype.config.ts` is `"valkey"`, the database is external, or the Postgres image is older than
17.2.9: then the stack runs a Valkey service instead.

| Variable | Default | Description |
|----------|---------|-------------|
| `SUPATYPE_KEYSPACE_PASSWORD` | Generated | **Required** when the cache is pg_keyspace on `supatype/postgres` 17.2.13 or later. The password of the keyspace user `supatype`, handed to the `db` and `server` services, and to `kong` when HTTPS is on |
| `SUPATYPE_KEYSPACE_PASSWORD_FILE` | None | A file on the host holding that password, in place of the variable. Mounted into `db` and `server`; not with HTTPS on. See [Passwords from files](#passwords-from-files) |
| `SUPATYPE_PROJECT_KEYSPACE_ADDR` | The stack's keyspace | `host:port` of a second keyspace for the response cache alone. Unset, the response cache uses the stack's keyspace |
| `SUPATYPE_PROJECT_KEYSPACE_USERNAME` | `supatype` | The user the server logs in to that second keyspace as |
| `SUPATYPE_PROJECT_KEYSPACE_PASSWORD` | None | The second keyspace's password. Unset, the server sends it no password. It never falls back to `SUPATYPE_KEYSPACE_PASSWORD`, and the server refuses to start when the two are the same |

`supatype init` writes a random `SUPATYPE_KEYSPACE_PASSWORD` into `.env`. Every `self-host compose`
command, and `supatype dev`, writes one when it is missing, and never replaces one that is there.
With the password in a file instead, none is written: see [Passwords from files](#passwords-from-files).
The compose file requires it, so `docker compose` run by hand without it stops with
`SUPATYPE_KEYSPACE_PASSWORD is missing from .env`. A Valkey service has no password: it is reachable on the compose network only.

To change the password, put the new one in `.env` and run `supatype self-host compose up -d`.
Compose recreates every service that receives it, so each starts with the new password. The cache
starts empty, which costs nothing but a few cache misses; the gateway's certificates are kept.

The three project keyspace variables are for a deployment that keeps cached responses in a keyspace
of their own, apart from the one holding the stack's shared state. The server reads them from
`.env` itself, so they need no change to the compose file. `SUPATYPE_PROJECT_KEYSPACE_PASSWORD`
must differ from `SUPATYPE_KEYSPACE_PASSWORD`, or the server stops at start with
`config: SUPATYPE_PROJECT_KEYSPACE_PASSWORD must differ from SUPATYPE_KEYSPACE_PASSWORD`.

### Passwords from files

Running the server or the `supatype/postgres` image yourself, you can give each password as a file
instead, the way `POSTGRES_PASSWORD_FILE` works for a Docker or Kubernetes secret:
`SUPATYPE_KEYSPACE_PASSWORD_FILE` (read by both the server and the image) and
`SUPATYPE_PROJECT_KEYSPACE_PASSWORD_FILE` (read by the server). One trailing newline is dropped,
and nothing else. Setting a password and its file together, or naming a file that is missing or
empty, stops the service at start with a message naming the variable or the file.

With the file, the database takes a new password with no restart: rewrite the file, then run
`SELECT pg_reload_conf();` in the database. The old password stops working at once. The server
reads its password when it starts, so restart it with the new one.

The stack the CLI generates (`supatype dev` with Docker, and `self-host compose`) takes the file
too. Set `SUPATYPE_KEYSPACE_PASSWORD_FILE` in `.env` or in the shell to a file on the host, either
absolute or relative to the project directory:

```bash
SUPATYPE_KEYSPACE_PASSWORD_FILE=./secrets/keyspace-password
```

The CLI then writes no `SUPATYPE_KEYSPACE_PASSWORD`, and the compose file mounts that file read-only
into `db` and `server` at `/run/secrets/supatype-keyspace-password` and gives both that path in
`SUPATYPE_KEYSPACE_PASSWORD_FILE` instead of the password. Before compose runs, the CLI stops with a
message when:

- both `SUPATYPE_KEYSPACE_PASSWORD` and `SUPATYPE_KEYSPACE_PASSWORD_FILE` are set, saying where each
  is set. A project that ran before has a generated password in `.env`: remove that line to use the
  file. The CLI never removes it for you.
- the file is missing, cannot be read, or holds no password.
- HTTPS is on (`server.tls`). Kong keeps its certificates in the keyspace and gets the password
  through its env vault, which reads environment variables only, so it cannot use a file. Keep the
  password in `.env` for an HTTPS stack.

On a Linux host the containers see the file with its host owner and mode, and the database reads
it as the image's `postgres` user, so make it readable to them (mode 0644 or 0444). A single file
mounted this way stays the file that was there when the container started: rewrite it in place to
change the password, since an editor that saves a new file in its place leaves the containers with
the old one until they restart.

`supatype init` run with `SUPATYPE_KEYSPACE_PASSWORD_FILE` set in the shell writes a comment in
place of the generated password. Native `supatype dev` reads the password from the file as well,
and hands it to its Postgres and server itself.

## Storage

By default the stack runs a SeaweedFS service for uploaded files, in the `storage-data` volume, and
the storage service gives each bucket an S3 bucket of its own there. The compose file passes the
storage service every S3 setting for it, so there is nothing to set.

To keep production files in an S3 bucket of your own instead, set `storage.production` in
`supatype.config.ts` (`supatype init` writes it when you answer "Production storage?" with S3):

```ts
storage: { provider: "local", local_path: ".supatype/storage", production: "s3" },
```

The stack then leaves SeaweedFS and its volume out, and runs the storage service in single-bucket
mode: every bucket is a key prefix inside `S3_BUCKET`, and public files are served by the storage
service, so the S3 bucket stays private. `storage.provider` is unaffected: it is where
`supatype dev` keeps files, and the Docker dev stack keeps its SeaweedFS either way.

| Variable | Default | Description |
|----------|---------|-------------|
| `S3_BUCKET` | None, required | The bucket. `self-host compose up` stops with a message while it is blank |
| `S3_REGION` | None | The bucket's region. Required on AWS, where `S3_ENDPOINT` stays blank |
| `S3_ENDPOINT` | None | The store's URL, for an S3-compatible store such as Cloudflare R2. The storage service runs in a container, where `localhost` is that container: for a store on the same machine use `http://host.docker.internal:<port>` with Docker Desktop, or the host's address (usually `172.17.0.1`) on Linux |
| `S3_ACCESS_KEY`, `S3_SECRET_KEY` | None | Keys that can read, write, list and delete objects in the bucket. Leave both blank on AWS to use the instance's or task's role |
| `S3_FORCE_PATH_STYLE` | `true` with an endpoint, `false` without | Whether the bucket goes in the URL path rather than the host name |

Set these in the server's `.env`, and use a different bucket from the one `supatype dev` uses.
Switching an existing stack to `production: "s3"` does not move its files out of SeaweedFS. See
[Storage](/docs/storage.html#own-bucket) for the bucket's layout, and for `S3_BUCKET_PREFIX` when
you run the storage service yourself with one S3 bucket per bucket.

## Images

Each service's image can be replaced from `.env`: `SUPATYPE_POSTGRES_IMAGE`, `SUPATYPE_SERVER_IMAGE`,
`SUPATYPE_STORAGE_IMAGE`, `SUPATYPE_FUNCTIONS_WORKER_IMAGE`, `SUPATYPE_REALTIME_IMAGE`,
`SUPATYPE_CONTROL_PLANE_IMAGE`, `SUPATYPE_STUDIO_IMAGE`, `SUPATYPE_ENGINE_IMAGE`,
`SUPATYPE_SEAWEEDFS_IMAGE` and `SUPATYPE_VALKEY_IMAGE`. Left unset, each service runs the image the
generated file names: for Supatype's own services, the exact release the CLI was tested with, never
`latest`, so upgrading the CLI moves them. A `versions` pin for
`engine` or `server` in `supatype.config.ts` writes `SUPATYPE_ENGINE_IMAGE` or
`SUPATYPE_SERVER_IMAGE` into `.env` for you.

## Generating keys

`supatype keys` signs `ANON_KEY` and `SERVICE_ROLE_KEY` with the `JWT_SECRET` in `.env` (or the one
you pass with `--secret`) and prints them:

```bash
npx @supatype/cli keys
```

| Flag | Effect |
|------|--------|
| `--write` | Write the keys into `.env` instead of printing them. Only blank keys are filled |
| `--force` | With `--write`, replace keys that already hold a value |
| `--exp-years <years>` | How long the keys are valid, in years. Default `10` |
| `--secret <secret>` | Sign with this secret instead of `JWT_SECRET` |

The command does not create `JWT_SECRET`: `supatype init` generates one, or use
`openssl rand -base64 48`. Use different secrets in every environment.
