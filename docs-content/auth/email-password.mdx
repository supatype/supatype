title: Email & Password
description: "Set up email and password authentication: sign up, sign in, confirmation, and password reset."

Email and password is the most common authentication method. Supatype handles sign-up, email confirmation, sign-in, and password reset out of the box.

## Sign up

```typescript
const { data, error } = await supatype.auth.signUp({
  email: "alice@example.com",
  password: "strongpassword123",
})
```

Whether the user must confirm their email before signing in is the auth server's
`SUPATYPE_MAILER_AUTOCONFIRM` setting. Out of the box it is on (auto-confirm): `supatype dev`
always enables it, and the self-host stack defaults to it, so `signUp` returns a session straight
away and no confirmation email is sent.

### Require email confirmation

On a self-hosted deployment, turn auto-confirm off in the project's `.env` and configure email
delivery (`email.provider` in `supatype.config.ts`, or the `SUPATYPE_SMTP_*` variables):

```bash
# .env
SUPATYPE_MAILER_AUTOCONFIRM=false
```

With auto-confirm off, `signUp` returns a user but no session, a confirmation email is sent, and
the user can sign in once they have clicked the link. There is no `supatype.config.ts` key for this
setting.

### Customize the confirmation email

Edit the email templates in Studio under **Authentication > Email Templates**. There is one
template each for signup confirmation, invites, password reset, magic links and email changes, and
they use Go template variables such as `{{ .ConfirmationURL }}`, `{{ .Email }}` and `{{ .Token }}`.

**Save template** stores the subject and HTML body in the project's database, in the
`auth.mail_templates` table, one row per template type. A saved template is used by every auth
server replica and survives a restart, and it wins over a template configured with the auth
server's `SUPATYPE_MAILER_TEMPLATES_*` and `SUPATYPE_MAILER_SUBJECTS_*` variables. Studio shows
when a saved edit is in force ("Saved edit in force since ..."); **Reset to default** deletes it,
and the configured template, or the built-in one when none is configured, is used again. An edit
saved on one replica reaches the emails the others send within ten seconds.

Before 0.7.0 a saved template lived only in the memory of the auth server that received it, so a
restart, or another replica, quietly went back to the configured template.

The same operations are on the auth admin API, with the service role key:
`GET`, `PUT` (a JSON body with `subject` and `body`, both required) and `DELETE` on
`/auth/v1/admin/template/<type>`, where `<type>` is `confirmation`, `invite`, `recovery`,
`magic_link` (or `magiclink`) or `email_change`. The `GET` answer carries `saved` and, when it is
true, `saved_at`.

## Sign in

```typescript
const { data, error } = await supatype.auth.signInWithPassword({
  email: "alice@example.com",
  password: "strongpassword123",
})

if (error) {
  console.error("Sign in failed:", error.message)
  return
}

// data.session contains the JWT
// data.user contains the user object
console.log("Signed in as:", data.user?.email)
```

## Password requirements

Passwords must be at least 6 characters by default. The auth server can require a longer minimum
(`SUPATYPE_PASSWORD_MIN_LENGTH`) or particular character classes
(`SUPATYPE_PASSWORD_REQUIRED_CHARACTERS`), but these are server settings: `supatype.config.ts` has no
key for them, and the generated stack does not set them.

## Password reset

### Send a reset email

```typescript
const { error } = await supatype.auth.resetPasswordForEmail(
  "alice@example.com",
  {
    redirectTo: "https://myapp.com/reset-password",
  }
)
```

### Handle the reset callback

When the user clicks the reset link, they are redirected to your app with a session in the URL.
Establish it, then update the password:

```typescript
// On your /reset-password page
await supatype.auth.getSessionFromUrl(window.location.href)

const { data, error } = await supatype.auth.updateUser({
  password: "newstrongpassword456",
})
```

## Server-side validation

All passwords are hashed with bcrypt before storage. Supatype never stores plaintext passwords. Rate limiting is applied to sign-in attempts to prevent brute-force attacks.

## Email rate limits

By default, the auth server limits email sending to prevent abuse:

| Limit | Default |
|-------|---------|
| Emails sent by the project (confirmation, reset, magic link and the rest together) | 30 per hour |
| Interval between emails to the same user | 60 seconds |

These are the auth server's `SUPATYPE_RATE_LIMIT_EMAIL_SENT` and `SUPATYPE_SMTP_MAX_FREQUENCY`
settings. Neither has a `supatype.config.ts` key.
